# Bug Report: UTF-8 BOM 未剥离导致解析失败或整文件误拒

**Type**: Untested flow
**Severity**: High
**Feature**: 002-schema-csv-mask
**Reported**: 2026-09-11
**Status**: Patched
**Patched**: 2026-09-11

## Description

带 BOM（`﻿` 前缀）的 UTF-8 文件是 Windows 记事本/Excel 导出的高发格式：

- JSONL：首行 `﻿{"id"...}` 无法解析 → 该行 `parse_error`，丢一条记录
- CSV：BOM 粘在首列名上变成 `﻿id` → 所有行因"缺失必填字段 id"被整体拒绝
- 外部 schema 文件、格式嗅探同样受影响

## Artifact Traceability

### spec.md (002)
- **Affected requirements**: FR-104（CSV 输入 UTF-8）、假设"字符编码: 输入输出均为 UTF-8"
- **Gap identified**: 未区分 UTF-8 与 UTF-8-BOM；对高发的 BOM 变体无容忍策略

### plan/research (002)
- **Affected sections**: research R-203/R-204（`open(..., encoding="utf-8")`）
- **Impact**: 全部输入读取路径改用 `utf-8-sig`（有 BOM 剥离、无 BOM 等价）

### tasks.md (002)
- **Missing tasks**: 新增修复任务（见 T019）

## Root Cause Analysis

规范假设只写了 "UTF-8"，实现按字面选择 `utf-8` codec；未考虑 Windows 生态导出文件普遍带 BOM。

## Recommended Fix

`read_jsonl` / `read_csv` / `detect_format` 嗅探 / `load_schema` 全部改用 `encoding="utf-8-sig"`；输出保持无 BOM 的 `utf-8`。
