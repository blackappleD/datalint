**功能分支**: `002-schema-csv-mask`
**创建时间**: 2026-09-10
**状态**: 草稿
**输入**: 用户描述: "1. 支持从外部 JSON 文件加载 schema，并对 schema 文件本身做校验，非法 schema 给出明确报错；兼容 CSV 输入，自动识别格式，输出格式可选 JSONL/CSV；2. 对无法解析的行不再中断，跳过并写入独立的 rejected 文件供人工复查；3. 新增 --mask 脱敏选项，对指定字段（如 email、phone）做掩码处理，支持模糊（contain）和精确（equal）两种匹配模式；4. 为以上功能补充单元测试，覆盖异常分支。"

## Clarifications

### Session 2026-09-10

- Q: --mask 的匹配模式（equal/contain）应如何指定？ → A: 每个字段模式独立标注：`--mask email:equal --mask phone:contain`（可重复给出选项，也支持逗号合写）；未标注模式时默认 equal；两种模式可在同一次运行中混用。
- Q: 匹配字段的值应按什么规则掩码？ → A: 统一首尾保留规则——值长度 > 4 时保留首尾各 1 字符、中间以等长 `*` 替代；长度 ≤ 4 时全部替换为 `*`；所有字段统一规则，不做邮箱/电话格式感知。
- Q: 未显式指定输入格式时，应如何自动识别 JSONL/CSV？ → A: 扩展名优先 + 内容兜底——`.csv` 识别为 CSV，`.jsonl`/`.json` 识别为 JSONL；其他/无扩展名时嗅探首个非空行（可解析为 JSON 对象 → JSONL，否则尝试按 CSV 表头理解）；仍无法判断时报错并提示显式指定输入格式。
- Q: --mask 应匹配哪些字段？ → A: 匹配记录中实际出现的所有字段名，包括 schema 未定义的透传字段——脱敏宁可多匹配，避免敏感数据从透传字段泄露。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 从外部 JSON 文件加载 schema (优先级: P1)

数据工程师的数据集结构各不相同，内置 schema 无法覆盖。他们希望编写一个 JSON 文件描述自己数据集的字段（名称、类型、是否必填、枚举取值），运行时通过选项指定该文件，工具即按此 schema 校验。如果 schema 文件本身写错了（JSON 语法错误、缺少必要声明、类型名不认识、枚举字段没给取值列表等），工具必须在开始处理数据前就给出指明具体问题的报错，而不是默默使用错误的规则。

**优先级原因**: 这是从"演示工具"到"通用工具"的关键跃迁——所有其他功能（CSV、脱敏）都在 schema 驱动的管道上运行；schema 可定制后工具才对真实数据集有用。

**独立测试**: 编写一个合法的自定义 schema 文件运行工具，验证校验规则按新 schema 生效；再分别构造各类非法 schema 文件，验证每种错误都得到指明位置和原因的报错且不产生输出。

**验收场景**:

1. **给定** 一个声明了不同字段集合的合法 schema JSON 文件, **当** 用户通过选项指定它运行, **那么** 数据按该 schema 的必填/类型/枚举规则校验，内置 schema 不生效。
2. **给定** 未指定 schema 文件, **当** 运行工具, **那么** 行为与之前完全一致（使用内置 schema），现有用户不受影响。
3. **给定** schema 文件不是合法 JSON, **当** 运行工具, **那么** 处理不开始，报错指明"schema 文件 JSON 解析失败"及原因，退出状态与参数错误一致。
4. **给定** schema 文件中某字段使用了不支持的类型名（如 `"type": "datetime"`）, **当** 运行工具, **那么** 报错指明字段名与非法类型名，并列出支持的类型。
5. **给定** schema 文件中枚举类型字段缺少取值列表（或取值列表为空/含非字符串）, **当** 运行工具, **那么** 报错指明该字段及问题。
6. **给定** schema 文件缺少字段列表、字段缺少名称、名称重复等结构性问题, **当** 运行工具, **那么** 各得到指明具体问题的报错。

### 用户故事 2 - CSV 输入与可选输出格式 (优先级: P2)

数据工程师手里既有 JSONL 也有 CSV 格式的数据集。他们希望直接把 CSV 文件喂给工具——工具根据文件自动识别格式并正确读取；同时希望能选择干净数据的输出格式（JSONL 或 CSV），以便对接不同的下游系统。

**优先级原因**: CSV 是结构化数据交换的第一大格式，支持后工具适用面倍增；依赖 schema 能力（US1）对 CSV 的纯文本值做类型转换。

**独立测试**: 用一份 CSV 文件（含表头）运行工具，验证记录被正确读取、校验、清洗；分别指定 JSONL 与 CSV 输出格式，验证两种输出内容等价。

**验收场景**:

1. **给定** 一个带表头行的 CSV 文件, **当** 用户不指定输入格式运行, **那么** 工具自动识别为 CSV，按表头将每行映射为记录并进入校验清洗管道。
2. **给定** 一个 JSONL 文件, **当** 不指定输入格式运行, **那么** 自动识别为 JSONL，行为与之前一致。
3. **给定** CSV 中数字字段列的文本值（如 `"95"`）, **当** 按 schema 校验, **那么** 该值按 schema 声明的类型转换后参与校验与输出（数字字段输出为数字）；无法转换的值按类型错误剔除。
4. **给定** 用户指定输出格式为 CSV, **当** 处理完成, **那么** 干净数据输出为带表头的 CSV 文件；未指定时默认输出 JSONL。
5. **给定** 自动识别无法确定输入格式（如内容既非合法 JSONL 首行又无法按 CSV 表头理解）, **当** 运行工具, **那么** 报错提示无法识别格式，并提示可通过选项显式指定输入格式。
6. **给定** 用户显式指定输入格式, **当** 运行工具, **那么** 跳过自动识别，按指定格式读取。

### 用户故事 3 - --mask 字段脱敏 (优先级: P2)

数据工程师处理含敏感信息（邮箱、手机号）的数据集，交付给下游前需要脱敏。他们希望通过 `--mask` 选项指定需要掩码的字段，并可选择两种字段匹配模式：精确（equal，字段名完全相等才匹配）与模糊（contain，字段名包含给定子串即匹配，如 `phone` 同时命中 `phone` 与 `home_phone`）。匹配到的字段值在干净输出中被掩码替换，原始值不出现在任何输出中。

**优先级原因**: 脱敏是数据交付的常见合规要求；独立于 CSV 功能，可与 US2 并行交付。

**独立测试**: 对含 email/phone 字段的数据分别以 equal 与 contain 模式运行 `--mask`，验证匹配字段的值被掩码、未匹配字段原样保留、两种模式的命中范围差异符合预期。

**验收场景**:

1. **给定** 记录含 `email` 字段且用户以精确模式指定掩码 `email`, **当** 处理完成, **那么** 干净输出中 `email` 的值被掩码（保留少量首尾字符、中间以掩码符替代），其他字段不变。
2. **给定** 记录含 `phone` 与 `home_phone` 字段且用户以模糊模式指定 `phone`, **当** 处理完成, **那么** 两个字段的值都被掩码。
3. **给定** 同样的数据以精确模式指定 `phone`, **当** 处理完成, **那么** 仅 `phone` 被掩码，`home_phone` 保持原值。
4. **给定** 掩码目标字段在某条记录中不存在或值不是字符串, **当** 处理该记录, **那么** 该记录正常输出，不报错（数字等非字符串值不掩码）。
5. **给定** 未指定 `--mask`, **当** 运行工具, **那么** 不做任何脱敏，行为与之前一致。
6. **给定** 指定了非法的匹配模式名, **当** 运行工具, **那么** 以参数错误报错退出。
7. **给定** 脱敏与去重同时启用且去重字段被脱敏, **当** 处理完成, **那么** 去重基于脱敏前的真实值判断（脱敏只影响输出，不影响质检语义）。

### 用户故事 4 - 不可解析行的持续处理与人工复查 (优先级: P3)

数据工程师的输入文件常混有损坏行（非法 JSON、CSV 列数不符等）。任何一行的解析失败都不应中断整个处理：损坏行跳过、写入独立的剔除明细文件（含行号、原因、原始内容）供人工复查，其余行继续处理。此行为须同时覆盖 JSONL 与 CSV 两种输入。

**优先级原因**: JSONL 路径此行为已存在，本故事将其扩展到 CSV 解析失败（列数不匹配等），并确保任何解析异常都不会导致整个运行崩溃。

**独立测试**: 构造 JSONL 与 CSV 各一份含损坏行的文件运行，验证处理完成（退出成功）、损坏行全部出现在剔除明细中、合法行全部正常输出。

**验收场景**:

1. **给定** CSV 文件中某行列数多于/少于表头列数, **当** 处理该文件, **那么** 该行剔除并记录"列数不匹配"原因与行号，处理继续。
2. **给定** JSONL 文件中混有非法 JSON 行, **当** 处理, **那么** 行为与之前一致：剔除、记录原因、继续（回归保障）。
3. **给定** 输入文件全部行都无法解析, **当** 处理完成, **那么** 干净输出为空、剔除明细包含全部行、以成功状态退出。

---

### 边界情况

- schema 文件路径不存在或不可读：以清晰错误报错退出（运行错误）。
- schema 文件为空 JSON 对象或字段列表为空：视为非法 schema，报错。
- 外部 schema 与 `--dedup-by`/`--mask` 联动：去重字段合法性按生效的 schema（外部或内置）判断。
- CSV 文件只有表头没有数据行：正常完成，total=0。
- CSV 表头含空列名或重复列名：报错提示 CSV 表头非法（无法建立可靠的字段映射）。
- CSV 值全部是字符串：布尔/数组等非标量类型不在 CSV 支持范围内；schema 类型转换仅涵盖数字与字符串/时间戳。
- 空文件的格式自动识别：无法判断时按报错处理并提示显式指定格式。
- 掩码值极短（1-2 个字符）：整个值以掩码符替代，不因保留首尾而泄露原值。
- `--mask` 模糊模式给出空字符串模式：视为参数错误（否则会命中所有字段）。
- CSV 输出时记录含 schema 外的额外字段：输出列集合为全部出现过的字段的并集按首条记录顺序，缺失值输出为空（见假设）。

## 需求 *(必填)*

### 功能需求

- **FR-101**: 系统必须支持通过命令行选项指定外部 schema JSON 文件；指定后以该 schema 完全替代内置 schema 参与校验、清洗、去重字段合法性判断；未指定时使用内置 schema，行为与现版本一致。
- **FR-102**: 系统必须在处理数据前校验 schema 文件自身的合法性，至少覆盖：JSON 语法、顶层结构、字段列表非空、每个字段有非空名称、名称不重复、类型名在支持集合内、枚举字段必须给出非空字符串取值列表、非枚举字段不得携带枚举取值；任何一项不满足即以指明具体字段与原因的错误信息终止，不产生任何输出文件。
- **FR-103**: schema 文件校验失败（结构非法）按参数错误处理；schema 文件不存在/不可读按运行错误处理。
- **FR-104**: 系统必须支持 CSV 输入（带表头、UTF-8）：表头行定义字段名，每个数据行映射为一条记录后进入既有校验清洗管道。
- **FR-105**: 系统必须在未显式指定输入格式时自动识别输入为 JSONL 或 CSV；无法识别时报错并提示用户显式指定；同时提供显式指定输入格式的选项以跳过自动识别。
- **FR-106**: 对 CSV 输入，系统必须按生效 schema 的字段类型对纯文本值做类型转换（数字字段转数字），转换失败按类型错误剔除；未在 schema 中声明的字段保持字符串。
- **FR-107**: 系统必须支持选择干净数据的输出格式为 JSONL（默认）或 CSV（带表头）；两种格式承载同样的记录内容。
- **FR-108**: 系统必须支持 `--mask` 选项指定一个或多个字段模式，每个模式可独立标注匹配方式（`模式名:equal` 或 `模式名:contain`，未标注默认 equal），选项可重复给出且支持逗号分隔合写，两种匹配方式可混用；equal 为字段名完全相等，contain 为字段名包含模式子串；匹配字段的字符串值在输出前被掩码（保留有限首尾字符、中间以固定掩码符替代，过短值全掩码），原始值不得出现在干净输出中。
- **FR-109**: 脱敏作用于记录中实际出现的所有字段（含 schema 未定义的透传字段），且仅作用于输出内容，不改变校验、去重、报告的判定语义（去重按脱敏前的值比较）；非字符串值与缺失字段不做掩码且不报错。
- **FR-110**: 非法的掩码模式名或空的字段模式必须以参数错误终止。
- **FR-111**: 任何单行解析失败（JSONL 非法 JSON、CSV 列数与表头不符等）不得中断处理：该行剔除、写入既有剔除明细文件（行号 + 错误类型 + 原因 + 原始内容），其余行继续。
- **FR-112**: 以上全部功能必须配有单元测试，覆盖率延续既有标准，且必须包含异常分支：非法 schema 各错误类别、格式识别失败、CSV 类型转换失败、列数不匹配、非法掩码参数。

### 关键实体

- **外部 Schema 文件**: 用户提供的 JSON 文档，声明字段列表（名称、类型、是否必填、枚举取值）；加载校验通过后与内置 schema 在管道中完全等价。
- **输入格式 (InputFormat)**: JSONL 或 CSV；由自动识别或用户显式指定确定，决定 reader 的解析方式。
- **掩码规则 (MaskRule)**: 字段模式集合 + 匹配模式（equal/contain）；作用于输出阶段，将匹配字段的字符串值替换为掩码形式。
- **剔除项 (Rejection)**: 沿用现有定义；新增 CSV 场景的解析失败原因（列数不匹配等），原始内容为该行原文。

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-101**: 用户可以不修改任何代码，仅通过编写一个 schema JSON 文件即让工具适配一个全新结构的数据集并完成质检全流程。
- **SC-102**: 对 10 种典型的非法 schema 文件（语法错误、缺字段列表、类型非法、枚举缺取值等），100% 得到指明具体位置或字段的错误信息，且均不产生输出文件。
- **SC-103**: 同一批数据分别以 JSONL 与 CSV 形式输入（内容等价），质检报告统计数字完全一致。
- **SC-104**: JSONL 与 CSV 两种输出格式承载的记录内容等价（字段与值一一对应），CSV 输出可被标准表格工具直接打开。
- **SC-105**: 启用 `--mask` 后，被匹配字段的原始值在干净输出文件中出现次数为 0；未匹配字段值 100% 保持原样。
- **SC-106**: 含任意比例损坏行的输入文件（JSONL 或 CSV）处理均以成功状态完成，损坏行 100% 出现在剔除明细中且附行号与原因。
- **SC-107**: 现有 v1 全部测试保持通过（无回归）；新增功能的异常分支均有对应测试用例。

## 假设

- **schema 文件格式**: 顶层为 JSON 对象，含 `fields` 数组；每个元素为 `{"name": str, "type": str, "required": bool, "enum_values": [str, ...]}`，其中 `required` 缺省为 false，`enum_values` 仅枚举类型必须提供；支持的类型名与内置 schema 一致（string / number / timestamp / enum）。
- **格式自动识别策略**: （已由澄清确认）扩展名优先——`.csv` → CSV，`.jsonl`/`.json` → JSONL；其他或无扩展名时嗅探首个非空行（可解析为 JSON 对象 → JSONL，否则尝试按 CSV 表头理解 → CSV）；仍无法判断时报错并提示显式指定。显式指定选项（如 `--input-format jsonl|csv`）跳过识别。
- **CSV 方言**: 标准逗号分隔、双引号转义、UTF-8、首行必须为表头；不支持无表头 CSV 与自定义分隔符（超出本期范围）。所有输入读取（JSONL/CSV/schema 文件/格式嗅探）必须容忍并剥离 UTF-8 BOM（Windows 记事本/Excel 导出常态）；输出不带 BOM。

  **Bugfix**: 2026-09-11 — [BUG-002] 补充 BOM 容忍要求：原实现按裸 `utf-8` 读取，BOM 导致 JSONL 首行 parse_error、CSV 首列名污染而整文件误拒。
- **默认输出路径派生**: 仅剥离 `.jsonl`/`.json` 扩展名；其他扩展名（含 `.csv`）保留完整文件名作为基底（`a.csv` → `a.csv.clean.jsonl` / `a.csv.rejects.jsonl`），避免 `a.jsonl` 与 `a.csv` 的默认输出互相覆盖。

  **Bugfix**: 2026-09-11 — [BUG-005] 原"去 stem"规则在同名不同扩展输入间产生输出碰撞。
- **CSV 输出列集合**: 按首条输出记录的字段顺序确定列；后续记录的额外字段追加在尾部；记录缺某列时输出空字符串。
- **CSV 空值语义**: CSV 单元格为空字符串时，可选字段视为缺失（不输出该字段/输出空），必填字符串字段的空串视为存在（长度为 0 的字符串合法）。
- **掩码算法**: （已由澄清确认）值长度 > 4 时保留首尾各 1 字符、中间全部替换为 `*`（数量与原长一致）；长度 ≤ 4 时全部替换为 `*`；所有字段统一规则，不做邮箱/电话格式感知的特殊处理。
- **--mask 参数形态**: 每个字段模式独立标注匹配方式（`email:equal`、`phone:contain`），未标注默认 equal；选项可重复给出，也支持逗号分隔合写；非法模式名（非 equal/contain）以参数错误终止。
- **contain 匹配大小写**: 不区分大小写（`Phone` 可被 `phone` 命中）；equal 模式区分大小写精确相等。
- **剔除明细文件**: 沿用现有 `<输入名>.rejects.jsonl` 机制（即用户所述"独立的 rejected 文件"），不新增第二个明细文件。为支持人工回溯，明细中的 `record` 始终为被剔除记录的原始未脱敏值（`--mask` 不作用于剔除明细）——该文件面向内部复查，不应直接对外分发；此权衡已在 README 中向用户声明。
- **报告与退出码**: 完全沿用 v1 契约；新增错误场景归入既有退出码语义（参数错误 2 / 运行错误 1）。
