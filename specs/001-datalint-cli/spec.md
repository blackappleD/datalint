# 功能规范: datalint — JSONL 数据清洗与质检 CLI

**功能分支**: `001-datalint-cli`
**创建时间**: 2026-09-10
**状态**: 草稿
**输入**: 用户描述: "本项目 datalint 用于实现 Python CLI，用于清洗和质检结构化数据集：读取 JSONL 文件；按内置 schema 校验（必填字段、类型、枚举值），非法记录剔除并记录原因；清洗（去除首尾空白、统一时间戳格式、按指定字段去重）；输出干净的 JSONL + 质检报告（总数/通过数/剔除数/各类错误计数），报告支持 JSON 或表格两种格式。限制：仅标准库 + pytest；模块拆分为 reader / validator / cleaner / reporter；含 README 与基本单元测试。"

## Clarifications

### Session 2026-09-10

- Q: 内置 schema 应采用什么字段定义？ → A: 采用示例 schema：`id`（字符串，必填）、`name`（字符串，必填）、`category`（枚举，必填）、`score`（数字，可选）、`timestamp`（时间戳，必填）。
- Q: 被剔除记录及其原因应如何交付给用户？ → A: 默认写入与输出同目录的剔除明细 JSONL 文件（每行含行号、错误类型、原因、原始记录），可通过命令行选项指定路径；报告中仅含分类计数。
- Q: 时间戳应统一为什么格式，支持哪些输入格式？ → A: 输出统一为 ISO 8601 UTC（如 `2026-09-10T08:00:00Z`）；识别的输入格式限定为三类：ISO 8601 变体、`YYYY/MM/DD HH:MM:SS`、Unix 秒级时间戳；其余格式的记录剔除。
- Q: 用户指定的去重字段不存在或在某条记录中缺失时如何处理？ → A: 去重字段必须是 schema 中定义的字段，否则 CLI 以参数错误退出（非零状态）；记录中可选字段缺失时按统一的"缺失值"参与去重比较。
- Q: 记录中出现 schema 未定义的额外字段时如何处理？ → A: 原样透传——schema 只校验已定义字段，未知字段不影响校验结果，清洗后保留在输出中（字符串值同样去首尾空白）。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 校验并剔除非法记录 (优先级: P1)

数据工程师拿到一份来源不可靠的 JSONL 数据集，希望一条命令即可剔除所有不符合 schema 的记录（缺失必填字段、类型错误、枚举值非法、无法解析的行），并得到每条被剔除记录的具体原因，以便回溯数据源问题。

**优先级原因**: 校验剔除是质检工具的核心价值——没有它，下游清洗和报告都失去意义。仅此一项即构成可用的 MVP。

**独立测试**: 准备一个混有合法与各类非法记录的 JSONL 文件，运行工具，验证输出文件只含合法记录、且每条被剔除记录均附带明确原因。

**验收场景**:

1. **给定** 一个包含 10 条记录、其中 3 条缺失必填字段的 JSONL 文件, **当** 用户运行质检命令, **那么** 输出文件包含 7 条记录，且 3 条被剔除记录的原因均标注为"缺失必填字段"并指明字段名。
2. **给定** 一条记录的某字段类型与 schema 不符（如期望数字却为字符串）, **当** 执行校验, **那么** 该记录被剔除，原因标注字段名与期望/实际类型。
3. **给定** 一条记录的枚举字段取值不在允许列表内, **当** 执行校验, **那么** 该记录被剔除，原因标注字段名与非法取值。
4. **给定** 文件中存在无法解析为 JSON 的行, **当** 执行读取, **那么** 该行被剔除并标注"JSON 解析失败"及行号，处理继续而不中断。

---

### 用户故事 2 - 清洗合法记录 (优先级: P2)

数据工程师希望通过校验的记录被自动规范化：字符串字段去除首尾空白、时间戳字段统一为标准格式、并可按指定字段组合去除重复记录，从而直接得到可入库的干净数据。

**优先级原因**: 清洗建立在校验之上，是"干净输出"承诺的第二半；无清洗时工具仅是过滤器。

**独立测试**: 准备含前后空白字符串、多种时间戳写法、重复记录的合法数据文件，运行工具并指定去重字段，验证输出记录已规范化且无重复。

**验收场景**:

1. **给定** 记录的字符串字段值带有首尾空白, **当** 执行清洗, **那么** 输出中该值的首尾空白被去除，字段内部内容不变。
2. **给定** 记录的时间戳字段以多种常见格式书写（如 `2026/09/10 08:00:00`、`2026-09-10T08:00:00Z`、Unix 秒级时间戳）, **当** 执行清洗, **那么** 输出中所有时间戳统一为同一种标准格式。
3. **给定** 用户指定按某字段（或字段组合）去重且文件中存在该字段值相同的多条记录, **当** 执行清洗, **那么** 仅保留首次出现的记录，其余记为"重复剔除"并计入报告。
4. **给定** 用户未指定去重字段, **当** 执行清洗, **那么** 不做去重，所有通过校验的记录均保留。

---

### 用户故事 3 - 生成质检报告 (优先级: P2)

数据工程师在处理结束后需要一份汇总报告：输入总数、通过数、剔除数、各类错误的分类计数，且可按需选择机器可读（JSON）或人类可读（表格）两种格式，用于流水线集成或人工审阅。

**优先级原因**: 报告让质检结果可度量、可追踪，是"质检"区别于"清洗"的关键交付物。

**独立测试**: 对同一输入分别以两种报告格式运行，验证两种输出中的统计数字一致且与实际处理结果吻合。

**验收场景**:

1. **给定** 处理完成的一批记录, **当** 用户选择 JSON 报告格式, **那么** 输出一份机器可读的报告，包含总数、通过数、剔除数及按错误类型分类的计数。
2. **给定** 同一批记录, **当** 用户选择表格报告格式, **那么** 输出一份对齐的文本表格，统计数字与 JSON 格式完全一致。
3. **给定** 输入文件全部记录合法, **当** 生成报告, **那么** 剔除数为 0，各错误类型计数为 0，通过数等于总数（去重后）。

---

### 边界情况

- 输入文件为空（0 行）：正常完成，输出空的干净文件，报告中总数为 0。
- 输入文件不存在或不可读：以清晰的错误信息终止，并返回非零退出状态。
- 空白行或仅含空白字符的行：直接跳过，不计入总数与剔除数。
- 一条记录同时存在多种错误（如既缺必填字段又有类型错误）：记录首个发现的错误原因并剔除，同一记录只计一次剔除。
- 去重字段不是 schema 中定义的字段：CLI 以参数错误终止（非零退出状态）；记录中可选去重字段缺失：按统一"缺失值"参与去重比较。
- 时间戳无法识别为任何支持的格式：该记录剔除并标注"时间戳格式无法识别"。
- 超大文件：逐行流式处理，不要求一次性载入全部内容。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须提供命令行入口，接受输入 JSONL 文件路径，并支持指定输出文件路径、去重字段、报告格式等选项。
- **FR-002**: 系统必须逐行读取 JSONL 文件，每行解析为一条记录；解析失败的行剔除并记录原因与行号，处理不中断。
- **FR-003**: 系统必须按内置 schema 校验每条记录：必填字段存在性、字段类型正确性、枚举字段取值合法性；任一校验失败即剔除该记录并记录字段级原因。schema 未定义的额外字段不参与校验、不导致剔除，并原样保留在输出中。可选字段值为显式 `null` 时视同缺失语义：跳过类型/枚举校验与时间戳归一，`null` 原样保留在输出中；必填字段值为 `null` 仍按类型错误剔除。

  **Bugfix**: 2026-09-11 — [BUG-006] 补充显式 `null` 语义：`required: false` 同时意味着 nullable，不再对可选字段的 `null` 报 type_error。
- **FR-004**: 系统必须对通过校验的记录执行清洗：去除所有字符串字段值的首尾空白。
- **FR-005**: 系统必须将时间戳字段统一转换为 ISO 8601 UTC 格式（如 `2026-09-10T08:00:00Z`）；输入含亚秒精度时必须保留（如 `2026-09-10T08:00:00.123Z`，去除尾零），不得静默截断；支持识别的输入格式为：ISO 8601 变体、`YYYY/MM/DD HH:MM:SS`、Unix 秒级时间戳；无法识别的时间戳导致该记录剔除并记录原因。无时区信息的输入按 UTC 处理，且系统必须在处理结束时向标准错误输出一次汇总提示（发生次数），不影响退出码。

  **Bugfix**: 2026-09-11 — [BUG-001] 补充亚秒精度保留要求（原实现秒级截断导致不同时刻归一相同，配合去重造成数据丢失）；[BUG-004] 补充 naive 时间戳按 UTC 假定的告警要求。
- **FR-006**: 系统必须支持按用户指定的一个或多个字段去重，保留首次出现的记录；未指定去重字段时不去重。指定的去重字段必须是 schema 中定义的字段，否则以参数错误终止（非零退出状态）；~~记录中可选字段缺失时按统一的"缺失值"参与去重比较~~ 任一去重字段在记录中缺失时，该记录跳过去重比较（始终保留，不判重也不注册键）。

  **Bugfix**: 2026-09-11 — [BUG-003] 推翻原澄清决策："缺失值参与比较"导致所有缺失该字段的记录互判重复而被批量静默剔除；改为缺失即跳过去重。
- **FR-007**: 系统必须将全部通过校验与清洗的记录写出为合法的 JSONL 文件，每行一条记录。
- **FR-008**: 系统必须生成质检报告，至少包含：输入总数、通过数、剔除数、按错误类型（解析失败/缺失必填字段/类型错误/枚举非法/时间戳无法识别/重复）分类的计数。
- **FR-009**: 报告必须支持 JSON 与表格两种输出格式，由用户通过选项选择；两种格式的统计数字必须一致。
- **FR-010**: 系统必须将每条被剔除记录写入一个剔除明细 JSONL 文件（每行包含行号、错误类型、原因描述及原始记录），默认与干净输出文件同目录，可通过命令行选项指定路径。
- **FR-011**: 输入文件不存在、不可读或参数非法时，系统必须输出清晰的错误信息并以非零状态退出；处理成功时以零状态退出。
- **FR-012**: 系统实现仅依赖语言标准库；测试仅依赖 pytest。
- **FR-013**: 代码必须按职责拆分为 reader（读取解析）、validator（schema 校验）、cleaner（清洗去重）、reporter（报告生成）四个模块。
- **FR-014**: 项目必须提供 README，包含安装步骤与运行示例；核心模块必须配有单元测试。

### 关键实体

- **记录 (Record)**: JSONL 文件中的一行，解析后为字段-值集合；是校验、清洗、去重与输出的基本单元。
- **Schema**: 内置的记录结构定义，声明必填字段、各字段类型及枚举字段的允许取值集合。具体定义为：`id`（字符串，必填）、`name`（字符串，必填）、`category`（枚举，必填）、`score`（数字，可选）、`timestamp`（时间戳，必填）；schema 集中定义在一处以便修改。
- **剔除项 (Rejection)**: 一条未通过处理的记录及其元信息——行号、错误类型、具体原因描述。
- **质检报告 (Report)**: 一次处理的统计汇总——总数、通过数、剔除数、按错误类型分类的计数；可渲染为 JSON 或表格。

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 用户通过一条命令即可完成"输入脏数据 → 得到干净数据 + 报告"的完整流程，无需任何中间手工步骤。
- **SC-002**: 对于含各类错误的混合输入，100% 的非法记录被剔除且每条均附带可定位的原因（行号 + 错误描述）；0 条合法记录被误剔除。
- **SC-003**: 输出文件中每一行都是合法 JSON 且符合内置 schema；字符串字段无首尾空白，时间戳格式全部一致。
- **SC-004**: 两种报告格式对同一输入产生完全一致的统计数字，且满足恒等式：总数 = 通过数 + 剔除数。
- **SC-005**: 10 万行规模的输入文件可在普通开发机上 60 秒内处理完成，且内存占用不随文件大小线性膨胀至不可用。
- **SC-006**: 新用户仅凭 README 即可在 5 分钟内完成安装并成功运行示例；单元测试覆盖 reader / validator / cleaner / reporter 四个模块的核心路径。

## 假设

- **去重保留策略**: 重复记录保留首次出现的一条（按文件行序）。
- **报告默认格式**: 未指定格式时默认输出表格（面向人工审阅），报告输出到标准输出，也可通过选项写入文件。
- **空白行处理**: 完全空白的行直接跳过，不计入总数与剔除数。
- **多错误记录**: 一条记录发现首个错误即剔除，只记一次、一个原因（快速失败）。
- **字符编码**: 输入输出均为 UTF-8。
- **运行环境**: 用户具备可运行现代 Python 3 的环境；不需要网络访问。
